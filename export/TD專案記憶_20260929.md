---
name: feedback-touchdesigner-technical-notes
description: Non-obvious TouchDesigner tool behaviors and MediaPipe-in-TD patterns discovered while building via the TD MCP server - apply to any future TouchDesigner work
metadata: 
  node_type: memory
  type: feedback
  originSessionId: 6e6196d1-8050-46cb-8ac0-e55f42e13106
  modified: 2026-09-16T07:31:49.615Z
---

Collection of TouchDesigner-specific gotchas discovered the hard way while building an interactive installation via the TouchDesigner MCP tools. Apply these directly rather than re-discovering them.

**Why each matters / how to apply:**

- **Cross-COMP references must use `selectTOP`/`selectCHOP` with a `.par.top`/`.par.chop` path, never a direct wire.** Attempting `nodeA.inputConnectors[0].connect(nodeB)` across different parent COMPs silently "succeeds" (no exception) but the input stays empty (`.inputs == []`) and downstream nodes error with "Not enough sources specified" or similar. Always tap cross-network data via a Select node in the local network instead.

- **`mirrorTOP` breaks on non-square-aspect canvases combined with `extend='mirror'`** — produces kaleidoscope/tiling duplication artifacts, regardless of `pivotx` value (tried both 0 and 0.5, same bug). Use `transformTOP` with `sx=-1` (and `sy=1`) for a horizontal flip instead — simple, reliable, no aspect-ratio dependency.

- **`feedbackTOP` needs an explicit reset pulse to start working.** Wire its input and set `.par.top` to the loop-closing node, then call `.par.resetpulse.pulse()` once — without it you get "Error: Not enough sources specified" forever, even though the wiring is correct.

- **Menu/enum parameter values often need empirical discovery via trial-and-check** (`.par.X = 'guess'; .par.X.eval()` to see if it stuck, since invalid values silently fall back to the previous/default rather than raising). Known-good short forms found this way: Math CHOP/TOP `chopop`/`preop`: `'sub'` (not `'subtract'`), `'mul'` (not `'multiply'`), `'root'` (square root), `'square'`. Threshold TOP `comparator`: `'less'`/`'greater'` work, but note the next point.

- **Threshold TOP's true/false → color mapping is inverted from intuition**: condition-TRUE maps to BLACK (0), condition-FALSE maps to WHITE (1). E.g. `comparator='less', threshold=X` makes pixels *below* X render black, pixels *above* render white — backwards from a naive reading of "select values less than X = white".

- **Only one `videodeviceinTOP` can hold a given physical webcam at a time.** A second instance pointed at the same device goes solid black (no error). When relocating/refactoring a camera-capture node, destroy the old one before expecting the new one to get a live feed.

- **MediaPipe in TD (via Script CHOP/TOP) needs the pip packages on `sys.path` manually**: TD's embedded Python has `site.ENABLE_USER_SITE = False`, so pip installs (which fall back to the user site-packages dir when Program Files isn't writable) aren't found until you `sys.path.append(r'C:\Users\<user>\AppData\Roaming\Python\Python3XX\site-packages')` at the top of the callback script, plus `importlib.invalidate_caches()` once after a fresh install in a running TD session.

- **MediaPipe Tasks API (`mediapipe.tasks.python.vision`, not the legacy `mp.solutions`)** is what recent `mediapipe` pip versions ship — `HandLandmarker`, `PoseLandmarker`, `ImageSegmenter`, each needs its own downloaded `.task`/`.tflite` model file from Google's model zoo (small, a few MB) and its own persistent instance (create once at Script-op module scope, reuse across cooks — recreating per-frame is far too slow).

- **`ImageSegmenter`'s selfie segmentation category mask polarity may be inverted from the documented 0=background/1=person** — verify empirically (`mask.astype(np.float32) < 0.5` vs `> 0.5`) by rendering and looking, don't assume.

- **Raw MediaPipe landmark `y` (no manual flip) already matches "1=top, 0=bottom" once fed a correctly-oriented image** — do not add an extra vertical flip "to be safe"; stacking flips silently cancels out and reintroduces the bug it was meant to fix. Verify orientation empirically with the user (ask them to raise a hand to a known screen position) rather than assuming a flip is needed.

- **`levelTOP`'s `brightness2` (Post page) only scales RGB, not Alpha** — silently. In a feedback-loop trail/persistence effect (`feedbackTOP` → `levelTOP(brightness2=decay<1)` → `compositeTOP(operand='add')` → back into the `feedbackTOP`), this means color dims correctly but Alpha never decays, so accumulated stamps stay fully opaque forever — looks like "the trail never fades, just keeps piling up" even though the math looks right and there are no errors. Fix: do the decay multiply with a **`mathTOP`**'s `gain` par (Multi-Add page) instead of `levelTOP.brightness2` — `mathTOP` applies its gain uniformly across R/G/B/A. Diagnosed by comparing `.numpyArray().max()` at each stage of the loop (`feedbackTOP` vs the decay node vs the composite) right after injecting a test value — if the decay node's max equals the feedback node's max unchanged, the multiply isn't touching the channel that actually controls visible fade (usually alpha). `care_first_state/silhouette_memory`'s `fadeTrail1` uses the same `brightness2`-on-levelTOP pattern and was never verified for this — worth rechecking if its memory-trail opacity ever looks like it doesn't fade.

- **MediaPipe VIDEO-mode (`detect_for_video`/`segment_for_video`) requires a strictly monotonically-increasing timestamp per call** — passing `int(absTime.seconds * 1000)` looks fine but `int()` truncation can produce the *same* millisecond on two back-to-back cooks, which throws `"Input timestamp must be monotonically increasing."` If that exception lands inside a bare `except Exception: store('last_error', ...)` (as in this project's callbacks), the whole frame silently goes blank/black (the canvas was zeroed before the try block and never gets filled) with no TD node error — reads as "detection randomly fails completely" rather than an exception. Diagnosed via `op(path).fetch('last_error', None)` — check any Script CHOP/TOP wrapping a MediaPipe call for a stored error message before assuming the model itself is inaccurate. Fix: track the last timestamp actually passed in the module's persistent `_state` dict, and clamp each new one to `max(int(absTime.seconds*1000), last_ts + 1)` before calling detect/segment. Affected every MediaPipe-based Script op in this project (`bodySegment1`, `handPose1`, `poseTrack1`, `handGrab1`) since they all copied the same timestamp line — worth checking any new one for the same pattern.

- **`body_sense/bodySegment1` already mirrors its own output internally** (`Mirrorx` custom par, `np.fliplr` in the script) before any downstream node touches it — it's the single shared silhouette-mask source for all 3 acts. Any downstream `transformTOP(sx=-1)`/`mirrorTOP` that ALSO flips it (as `silhouette_memory/flipSil1`, `feeding_visual/mirrorBody2`, `card_visual/mirrorBody3` all did) double-flips and cancels back to unmirrored — while the hand/pose tracking coordinates (`handPose1`, `poseTrack1`, `handGrab1`, each with their own `Mirrorx` par) only flip once and stay correctly mirrored. Net effect: the visible body silhouette renders in the RAW camera orientation while the light/hand/card tracking is mirror-correct, so the two visibly disagree ("left/right feels backwards") even though every individual `Mirrorx` flag looks right in isolation. Diagnosed by tracing each flip node's input chain back to its `.par.top`/wire source and checking whether an ancestor already flips — don't just check one node's own flag. Fix: mirror ONCE at the shared source (`bodySegment1`) and leave every downstream consumer's own flip disabled (`sx=1`) — treat any *new* consumer of `bodySegment1` the same way, don't reflexively add a flip "to be safe."

- **Tinting a mask/edge-outline by `compositeTOP`-'add'-ing a full-frame `constantTOP` color washes the ENTIRE canvas, not just the shape** — a `constantTOP` is opaque and uniform everywhere, so `add`-compositing it onto a mostly-black edge/mask TOP adds that color to every pixel, including the background (confirmed via `numpyArray()`: every one of 65536 px was >0.05, not just the ~1300 px actually on the edge line). Downstream `gain`/`brightness` dimming (e.g. to 12%) makes this read as a faint, uniform, ALL-OVER wash rather than "no color except on the line" — easy to miss visually since it's subtle, but it silently floods brightness across the whole frame and can look like stray blobs/noise once combined with other layers (vignettes, glows) rather than obviously wrong on its own. Fix: use `operand='multiply'` instead of `'add'` to tint — multiplying a near-black background by the tint color keeps it near-black, while multiplying the bright edge/mask by the tint color colors only that shape. Diagnosed by counting nonzero pixels in the output (`(arr>threshold).sum()`) and comparing to the canvas size — full-canvas-nonzero is the tell, not just eyeballing a thumbnail.

- **Checking "does this node have downstream consumers" via `outputConnectors[0].connections` only catches WIRED consumers — a Script CHOP/TOP that reads another node via `op(path)` in its Python code (not a wire) won't show up there, so a node can look like a dead-end orphan and still be live-consumed.** This caused a real bug: `chest_alignment/flipMask1` had zero wired outputs (looked orphaned, was left alone during a double-flip mirror cleanup earlier in this project), but `chestAlign1`'s callback script reads it directly via `op(MASK_PATH)` as a fallback silhouette source whenever pose tracking fails (`pose_found < 0.5`, which — given how often the pose confidence runs low in this setup — happens often). `flipMask1` still had its own redundant `sx=-1` on top of the already-mirrored `bodySegment1` source, so every time chest tracking silently fell back to the mask heuristic, the reported chest/bowl position flipped to the wrong side — an intermittent, hard-to-reproduce "mirror is backwards sometimes" bug. Confirmed by checking `pose['pose_found'].eval()` at the moment of the reported glitch (it was 0, i.e., mid-fallback) rather than assuming the primary path was always active. When auditing a node for redundant flips/consumers, grep the DAT source of every sibling script op for `op(` references to it, not just the wire graph.

- **A pure-multiplicative decay (`mathTOP.par.gain < 1` each frame, e.g. for a fading feedback trail) is asymptotic — it never reaches true zero, only ever gets closer.** With continuous input at many different screen positions over an extended session (someone moving their hand around for a while), each position's individual peak decays fine, but the union of all their long faint tails can end up covering most of the canvas at a very low level (confirmed via `(arr>0.005).sum()` returning ~68% of total pixels while `.max()` still read a normal-looking small number) — reads on a real display as a faint, hard-to-pin-down color-cast/haze across the image ("doesn't fully fade") even though the peak-brightness spot-check looks fine. A single `.max()` check hides this; check the nonzero-pixel *count* at a low threshold too. Fix: add a small constant subtraction (`postoff`, e.g. -0.006) alongside the multiplicative `gain` in the same decay node — this makes the decay reach exact zero in bounded time instead of an infinite tail, and negative results clamp to black on display. Needed one manual hard-reset (temporarily setting `gain=0` for a frame) to clear the pre-existing accumulated haze after adding the fix, since the fix only prevents new haze, doesn't retroactively clear old.

- **A `transformTOP`(sub-pixel shift) → `feedbackTOP` loop blurs progressively every single frame** if `filtertype`/`inputfiltertype` are left at the default `'linear'`. Each frame resamples the previous frame's (already-resampled) image with bilinear interpolation; over hundreds of frames (e.g. an 8-second scroll at 60fps = ~480 iterations) the interpolation blur compounds into a heavy smear, even though nothing looks wrong in any single node's parameters or errors. This bit a scrolling-line/oscilloscope-style effect (`transformTOP` shifting a canvas left each frame, composited with a fresh sample, fed back) — the line started sharp and got unreadably blurry the longer it scrolled. Fix: set `filtertype='nearest'` (and `inputfiltertype='nearest'` where present) on every node inside the feedback loop (the shift TOP, the composite, and the feedbackTOP itself) — point-sampling doesn't accumulate blur across iterations. Trade-off is minor aliasing/jitter on sub-pixel shifts, which reads far better than accumulating blur for thin lines/text. Any TD feedback loop that does a **sub-pixel transform every frame** (scroll, slow rotate, slow scale) is a candidate for this — worth checking `filtertype` up front rather than discovering it after the blur has already been "designed around."

- **The fix that actually made this project playable: ONE GPU-downscaled camera shared by every MediaPipe detector.** Each detector had its own `cam.numpyArray()` of the full 1280x720 frame plus its own `(arr*255).astype(uint8)` and `cv2.resize` - the same per-frame preprocessing done three or four times over, all on the CPU. Inserting a `resolutionTOP` (`care_first_state/camSmall1`, 480x270) after `cam1` and pointing every detector's `CAM_PATH` at it took Act 1 from 6.3 fps to 43.5 fps (2026-09-16), while at the SAME time raising the internal canvas from 256x256 to 1280x720. Related traps found the same day: (1) **a per-frame inference rate cap does nothing while the cap is higher than the achieved frame rate** - capping at 10-20Hz while the project ran at 5 fps meant every frame was still "due"; the cap only starts skipping once the frame rate rises above it, so caps and per-frame cost reductions have to be done together, and the win looks like a virtuous cycle; (2) `numpyArray(delayed=False)` is a blocking GPU->CPU sync - `keepLargestBlob1` did one every frame in all three acts for an image only Act 1 displays; (3) `.cook(force=True)` returns before the GPU finishes, so wall-clock timing around it measures nothing - measure achieved frame rate instead as `op.totalCooks` delta over `absTime.seconds` delta across SEPARATE tool calls (`absTime` does not advance within one script), and sanity-check by bypassing the suspect nodes to find the ceiling.

- **A Script TOP that writes a small "blank" when idle drags the whole downstream composite chain down to that size.** `crackDraw1`/`ecgDraw1` wrote a 4x4 array while their act was off screen, and `addCrack1`/`addEcg1` inherited 4x4 - harmless while hidden, but the incoming act is composited at that size during the 2.5s crossfade INTO it. Either write the blank at full resolution (what `kintsugiDraw1` does) or, better, `return` without calling `copyNumpyArray` at all: the TOP keeps its previous texture, which costs nothing and cannot change the resolution.

- **Detectors shared across acts leak gestures into OTHER acts' state machines — gate every act-specific state machine by scene, and reset it on entry.** All state-machine Script CHOPs here are `CookLevel.ALWAYS`, so they keep reading live input even while their act is hidden, and several detectors are deliberately shared (`handGrab1` runs in Act 2+3, `poseTrack1` in Act 1+3). Found 3 real leaks this way on 2026-09-15: Act 2's bowl pinch (the bowl sits almost exactly on Act 3's card-slot screen position) placed and permanently latched Act 3's card lock before Act 3 began; Act 3's card-draw pinch could register phantom Act 2 feeds; and feeding kept counting after the bowl/mouth lights had faded to alpha 0. Symptom the user noticed: "Act 3's card is already locked when Act 3 starts." Fix pattern: at the top of `onCook`, check `switchScene1.par.index` against the node's own `ACTIVE_SCENE_INDICES`; when inactive, skip reading inputs and emit frozen state; on the inactive->active edge, reset `_state`. Also gate on what the visitor can actually SEE (feeding locks the moment `weary` hides the target lights). Gating the expensive *detector* by scene is not enough when a *consumer* of it isn't gated. Verify with a fake-CHOP injection test run in both scenes, and restore/cleanup inside the SAME script call — fakes left wired between MCP calls get cooked by TD's live loop and pollute counters (`feeding_count` jumped to 22 that way).

- **`errors()` does NOT include Python script errors — use `scriptErrors()`.** A red circle-X badge on a node in the network editor (it propagates up through every parent COMP tile, so it can appear on a Base COMP three levels above the real source) can come from a script error that `op.errors(recurse=True)` reports as empty forever. Found this way: `care_first_state/emotional_fx/ecgDraw1_callbacks` line 76, `AttributeError: NoneType object has no attribute eval` — the badge sat there unexplained while every error scan came back clean, including a 300-frame sampler looking for transient errors. Scan with `op.scriptErrors(recurse=False)` over a hand-rolled `.children` walk, and clear with `op.clearScriptErrors(recurse=False, error='*')` once fixed — the message persists in the UI long after the condition is gone.

- **`chop['channel_name']` returns None when the CHOP has not cooked yet, so `chop['x'].eval()` crashes at load** even when guarded with `if chop is not None` — the node exists, the channel does not. A load-time race: `poseTrack1` has all 12 channels once running, so it fires once at startup and leaves a stale badge. This project uses that idiom in 59 places; the fragile ones read a Script CHOP that may not have cooked yet. Safe form: `ch = chop['name'] if chop is not None else None` then `val = ch.eval() if ch is not None else default`.

- **Measuring frame rate: `absTime.seconds` is NOT wall-clock time** — it is derived from the frame counter (`absTime.seconds == absTime.frame / project.cookRate` exactly), so `delta(node.totalCooks) / delta(absTime.seconds)` measures "what fraction of TD frames that node cooked, times 60", not fps. Useful as a ratio (it is how the 6.3 -> 43.5 work was tracked) but it is not a frame rate, and it collapses for a node nothing displays: `masterOut1.totalCooks` barely advances while the output window is closed, which read as "the project dropped to 10 fps" when nothing was wrong. True fps = `delta(absTime.frame) / delta(time.time())`. Even that is contaminated when MCP calls fall inside the interval (each one blocks TD): sampling across two tool calls gave 57.5 / 41.9 / 32.6 fps for an unchanged project. Measure inside TD instead — store `(absTime.frame, time.time())`, schedule `run(..., delayFrames=400)` to compute the ratio into storage, make no MCP calls while it runs, then read and unstore it. That gave a stable 51.75 fps.

- **`windowCOMP`'s `size='fill'` does not fill the display — it opens the window at the COMP panel size** (237x39 here, which the user saw as a tiny sliver in the corner of their screen). Use `size='custom'` with explicit `winw`/`winh`. Units follow `dpiscaling`: with `usedpiscale` on a 150%-scaled display, `winw/winh = 1280x720` produces a true 1920x1080 native client area. A window COMP's own `.width`/`.height`/`.x`/`.y` report the COMP *panel*, not the OS window, so they cannot verify any of this — measure the real window from outside with Win32 `GetClientRect` from a DPI-aware PowerShell snippet (a DPI-unaware process reports logical pixels and lies by the scale factor). Other traps: `justifyv='top'` offsets are y-up, so a positive `winoffsety` pushes the title bar off the top of the screen; `bordersinsize=True` makes borders eat into the client area and breaks the 16:9 fit; a window left over from a previous session can report `isOpen=True` while minimised at x=-32000; and size changes need a `winclose` pulse and a frame before `winopen`.

- **Compositing an opaque full-canvas `constantTOP` with `operand='add'` puts a hard ceiling on contrast, not just a wash.** Both the tinted shape and the background clamp at 1.0, so after a downstream dim they land at almost the same value — measured 1.07x (line 0.1255 vs background 0.1176) in `silhouette_memory`. No amount of blur reduction or edge-resolution increase makes the line pop while that add stays, which is worth saying out loud instead of quietly switching to `multiply`: on this project that wash is the intended background colour — see [[feedback-respect-user-design]].

- **Forcing an un-triggered effect for screenshots: rename the state CHOP and drop a same-named `constantCHOP` in its place.** Visuals here read state by path (`op('.../wearinessState1')['cloud_alpha']`), so renaming the real Script CHOP to `X_bak` and creating a constant named `X` with **every original channel copied** (only the wanted ones overridden) redirects all path lookups with zero edits to the artwork, and restoring is `destroy()` + rename back. Copy all channels or consumers hit the `chop['name']` -> None crash. **Blind spot: consumers connected by a WIRE keep reading the renamed original** — `card_sense/cardState1` feeds `cardSenseOut1` by wire, so faking `cardState1` changed nothing and the fake had to move to `cardSenseOut1`, the node the select reads by path. Second hazard: a consumer may reach into the node object itself, not just its channels — `ecgDraw1_callbacks` line 37 does `op(pv.par.callbacks.eval())` to replay the pulse curve, which a constantCHOP has no `callbacks` par for, so faking `pulseValue1` blanked the ECG and threw. Grep the DATs for `.par.callbacks` (one hit project-wide) before choosing an injection point. Latched state machines also need their trigger EDGE, not just a level: `crackDraw1` only generates crack geometry when `recoil` crosses 0.02 upward, so set the fake to 0, `cook(force=True)`, set it to 0.6, `cook(force=True)`.

- **A `circleTOP`'s `softness` is absolute, not relative to the shape, so a thin shape with a large softness renders as literally nothing** (alpha max exactly 0.0, no error, no warning). `ceremony_light/ray0..ray9` have `radiusx=0.012` with `softness=0.6` — 50x the half-width — so the Act 1 ray burst has never once been visible in the finished piece. Diagnosed by confirming `fillalpha` evaluated to 1.0 and the fill colour was non-black while `numpyArray()` came back all zeros, then setting `softness=0` and watching alpha jump to 1.0. Any generator TOP (circle/rectangle) whose size parameter is much smaller than its softness deserves the same check.

- **A one-frame pulse channel is unreliable between Script CHOPs that have no cook-order dependency.** `feedingState1` raised `feeding_triggered` for exactly one frame; the three consumers reading it with `.eval()` caught roughly one feed in five (23 feeds -> 4 cracks) because TD does not guarantee which of two independent `CookLevel.ALWAYS` nodes cooks first. Any state a sibling node must not miss belongs in a **monotonic counter** (watch for an increase) rather than a momentary flag.

- **Two Script CHOPs that read each other form a cook dependency loop, and TD resolves it by handing one of them a channel-less CHOP: `chop['name']` returns None mid-frame.** Wrapped in the usual `except Exception: store('last_error', ...)`, the entire block dies silently every frame - here `weary` stayed 0 forever so the Act 2 clouds could never appear, with no node error and nothing on screen to explain it. The tell is `op.fetch('last_error')` holding `'NoneType' object has no attribute 'eval'` while TD's own "Cook dependency loop detected" warning sits on the other node. Fix: pass the value through **storage** (`store()` on the producer, `fetch()` on the consumer) - storage creates no cook dependency, and this project already used that idiom in the other direction (`weary_cached`).

- **Two proximity zones that can overlap on screen turn a sequential gesture gate into a per-frame oscillator.** `bowl_touched -> carrying -> mouth_reached -> feed -> carrying=False` re-armed the instant the hand sat inside both radii, scoring a feed every other frame (3 feeds in 0.05 s, 23 from one gesture). A sequence gate needs an explicit "left the second zone" latch before it can re-arm, not just the sequence itself.

- **A state machine with an auto-reset makes live state reads lie.** Act 3's embrace latched, filled the gold to `front=1.0`, then `Autoresetseconds=10` cleared `embraced`/`held_seconds` back to 0 - so every state read I took after the fact said "it never happened", three times in a row, while the visitor could see it working. When the user says an effect fires and the instrumentation says otherwise, **look at the captured frames** (pixel counts, saved PNGs) before doubting them: the artifact outlives the state. Also never run two self-rescheduling `run()` probes against the same storage key - they fetch/modify/store the same dict and silently clobber each other's maxima.

**compositeTOP input shifting (2026-09-22):** multi-input TOPs keep a packed input list - `inputConnectors[0].disconnect()` slides input 1 down into slot 0, so a following `inputConnectors[0].connect(x)` REPLACES what used to be input 1 (it silently removed the whole scene from `addSubtitle1`; only the text was left). To swap one input: record all inputs, then reconnect each slot explicitly, and re-read the input list afterwards. Also: `absTime.frame` advances with wall time even when frames drop, so `frames/seconds` always reads 60 - measure real fps with `totalCooks` of a CookLevel.ALWAYS node (a null TOP may skip cooks when its image is unchanged).

**NVIDIA Maxine nodes in TD (2026-09-22):** `nvidiabackgroundTOP` needs the NVIDIA Video Effects SDK and `bodytrackCHOP` the AR SDK 0.8.7.0 (user installed both for the RTX 5060; before that both error "TensorRT not found"). After install both loaded (background: ~0.85 ms CPU / ~6 ms GPU, first cook ~2.1 s model load) but still output nothing on the first forced cooks. **Force-cooking BOTH of them every frame from a `run(..., delayFrames=1)` pump deadlocked TouchDesigner** (Not Responding, 0% CPU, 0% GPU - a true deadlock, not an engine build). Next time: test one Maxine node at a time, let TD pull it normally (wire to a null / viewer), never `cook(force=True)` them in a loop, save before trying.

**Script-error records are sticky and NOT in `errors()` (2026-09-22):** a Python exception inside a DAT callback (e.g. ecgDraw1_callbacks during a fake-CHOP injection test) is stored as a *script error* on the DAT and shows a red X on it and every parent COMP, even after the cause is gone. `op.errors()` does not report it - check `op.scriptErrors()` over the tree, and after every injection test run `op('/project1').clearScriptErrors(recurse=True)`, then re-check a few seconds later to prove it does not come back. The user noticed the red X before I did.

**Recording the piece to video (2026-09-23):** TD non-commercial **cannot** use `movieFileOut` h264/h265 ("GPU Accelerated H.264/H.265 Encoding requires a Commercial license") - record MJPEG (`videocodec='mjpa'`, mov container, ~2.5 MB/s at 1280x720) and transcode afterwards. TD ships `bin/ffmpeg.exe` + `bin/ffprobe.exe`, but that build has **no libx264**; `h264_qsv` (Intel QSV) works and gave 32 MB for 6:18 at `-global_quality 23`. Timing came out exact (22681 frames / 378.02 s = 60 fps), so no re-timing was needed - still worth checking `nb_read_frames` against the wall-clock length of the run. For an unattended run, drive the beats from a temporary Execute DAT on `onFrameStart` keyed to `sceneTimer1['elapsed_seconds']` and have it stop the record and set `me.par.active = False` at the end, rather than babysitting with MCP calls. **`relief` only accumulates while `press_depth > 0`** (`wearinessState1_callbacks1` line ~186) - with a person merely sitting in frame the hand pose can register as a press and quietly cool Act 2 seconds after the burst; pin `_state['relief']` when a run needs the climax to hold.
